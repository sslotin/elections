# Тестовые данные: флешка 2026-09-18

Содержимое флешки: официальные почасовые выгрузки одного голосования плюс
скрипты из `parser/`, которые должны лежать на такой флешке. В репозитории
лежит копия того же каталога, файлы не менялись — сверяется через `sha256sum`.
Файл одинаковый и на флешке, и в репозитории.

## Что внутри

| файл | что это |
|---|---|
| `2V8q3LAJqY6cYzCSAkhyeSomQGqEaA9KQtGjjWWRs537_2026-09-18_*.zip` | почасовые официальные выгрузки одного голосования: один `.csv` + один `.sig` внутри каждого архива |
| `SHA256SUMS` | контрольные суммы архивов, `sha256sum -c SHA256SUMS` |
| `monitor/` | монитор блокчейна (`monitor.py`, `search-transaction.py`) — байт-в-байт как `parser/monitor/` в репозитории. Внутри есть пустые `__pycache__/` и `block-monitor/shard-0/`: монитор на флешке запускали, но блоков он не сохранил (в `block-monitor/` нет ни `manifest.json`, ни chunks).
| `dump-chunked.py` | потоковый дамп блоков для запуска на ноутбуке в помещении ОП РФ (скрипт пишет рядом с собой) |
| `parse.py` | нарезка стандартных CSV-таблиц из дампа + метаданных портала |

`dump-chunked.py` и `parse.py` — копии файлов из `parser/`; правки надо вносить
в `feddeg/parser/` основного репозитория и копировать заново, а не сюда.
В публикации одного `verification/` эти копии сохранены для происхождения
данных и не требуются для запуска официального верификатора.

Носитель — exFAT (файловые права не сохраняются, `dump-chunked.py` и
`monitor/*.py` приходится запускать как `python <файл>`). При копировании в
репозиторий флешка была примонтирована как `/media/sereja/4499-AB75`; кроме
перечисленного, на ней лежал только служебный каталог Windows
`System Volume Information/`, он не копировался.

## Проверка официальной утилитой РТК

Выгрузки кладутся в каталог как есть и подаются утилите наблюдателя (сборка и
запуск — см. `../README.md`; нужен КриптоПро CSP **5.0.13000**, на
5.0.12000 операции на кривой молча ломаются и все слепые подписи «не проходят»):

```sh
docker run --rm --memory=8g --cpus=16 \
  -v "$PWD:/app/files:ro" observer-tool run validate \
  2V8q3LAJqY6cYzCSAkhyeSomQGqEaA9KQtGjjWWRs537
```

Результат на этих данных (18 сентября 2026, 4,9 с на 16 ядрах):

- выдано бюллетеней 1164, принято контрактом 1161, отклонено 0
- некорректных подписей транзакций 0, слепых подписей 0, ZKP 0, переголосований 0
- зашифрованная сумма по 1161 действительному бюллетеню считается
- итог сверить нельзя: `Error: Не хватает данных для проверки расшифровок.` —
  в окне нет публикации `results`. Строка «Результаты не совпадают: 1» в этом
  случае означает именно отказ проверки, а не расхождение; блок «ОБЩИЙ ИТОГ» с
  нулями — известный баг утилиты (сводка не наполняется, если проверка
  голосования упала после печати частного итога).

Независимая проверка тем же окном (собственный верификатор на Python,
`python3 -m pydeg audit <zip>`; каталог `pydeg` лежит вне этого репозитория)
даёт те же числа и совпадение `KeyAgg`.

## Что заметно в самих данных

- **Часы в именах файлов идут на 4 часа вперёд относительно MSK.** Файл
  `..._0800-0900.zip` содержит транзакции 04:00:23–04:59:41 MSK, то есть подписи
  в именах — это UTC+7, а не московское время. Часы внутри выгрузки стыкуются
  друг с другом без разрывов.
- Окно обрывается на 09:58:51 MSK. Выгрузок за 03:00–08:00 (по подписи в
  имени) нет, потому что в эти часы не было транзакций: первый `vote` прошёл в
  04:00:23 MSK, тогда как `startVoting` — в 22:22 MSK предыдущего дня.
- Колонка `rollback` во всех 2372 строках равна `1`; утилита считает
  откатом только `-1`, так что это просто «не откат».
- `.sig` (1182 байта, DER) лежит рядом с каждым `.csv`, но утилита его не
  проверяет: она читает только `*.csv`. Содержимое строк защищено подписями
  самих транзакций, однако отсутствие транзакции в выгрузке проверить нечем.
- 3 выданные слепые подписи остались без голоса (1164 против 1161).
