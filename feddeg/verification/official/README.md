# Официальная проверка ДЭГ

Адаптер выгрузки блокчейна к формату официальной утилиты наблюдателя от РТК (https://github.com/cikrf/deg2025/tree/main/observer-tools) и вспомогательный скрипт для запуска по батчам. Саму утилиту и CryptoPro CSP нужно поставить отдельно; `cpblindsig.zip` уже лежит в этом каталоге.

(Дальше описание сгенерировано ИИ. В ростелекомовский код я не особо погружался и гарантировать корректность не могу.)

## Что подается на вход

`dump_to_official.py` принимает:

- исходный JSONL-дамп (`edg2025.json`),
- ZIP с одним JSONL-файлом (`edg2025.zip`),
- gzip-файл или каталог с JSONL-частями.

Пример для полного дампа:

```text
python3 feddeg/verification/official/dump_to_official.py \
  --dump /data/edg2025.zip \
  --out /data/edg2025-official
```

Результат:

```text
/data/edg2025-official/
├── files/<contract-id>.zip       # CSV внутри каждого архива
└── manifest.json                 # размеры, хеши и счетчики операций
```

Исходный дамп читается потоково и не изменяется. Скрипт откажется писать в
существующий каталог; `--force` удаляет его перед повторной генерацией.
Для проверки одного голосования можно существенно сократить промежуточные
данные:

```text
python3 feddeg/verification/official/dump_to_official.py \
  --dump /data/edg2025.zip \
  --out /data/one-voting \
  --contracts D6amFqdazz8DxfxUxmFZKpFioXhhEXQ3jkgRMeab1A4t
```

У исходного дампа и у подготовленного набора может быть несколько гигабайт,
поэтому `--out` лучше размещать на диске с достаточным свободным местом.

## Установка официального инструмента

Следуйте README репозитория `cikrf/deg2025/observer-tools` для получения:

1. исходников `observer-tools`;
2. CryptoPro CSP 5.0 R3 для Linux x64;
3. `cpblindsig.zip` от CryptoPro.

Архив CSP скачивается при сборке и не хранится в репозитории. `cpblindsig.zip`
уже включён как зависимость воспроизведения; это проприетарная библиотека,
не часть открытого кода проекта. Перед перепубликацией проверьте условия её
распространения.
Официальный Docker-вариант обычно проще всего воспроизвести:

```text
cd /path/to/deg2025/observer-tools
# Положите сюда linux-amd64_deb.tgz и cpblindsig.zip,
# как описано в официальном README.
docker build -t observer-tool -f Dockerfile .
```

Для Intel/AMD запуск одного голосования из подготовленного набора:

```text
cd /data/edg2025-official
docker run --rm -ti \
  --memory=16g --cpus=10 \
  -v "$PWD/files:/app/files" \
  observer-tool run validate \
  D6amFqdazz8DxfxUxmFZKpFioXhhEXQ3jkgRMeab1A4t
```

Если идентификатор не указан, текущая версия инструмента пытается проверить
все ZIP в `files/`. Для больших наборов сначала проверьте одно голосование и
увеличьте выделенные Docker ресурсы при необходимости. На Apple Silicon
добавьте `--platform linux/x86_64` к `docker run` и `docker build`, как в
официальном README инструмента.

### Нативный запуск и пакетный режим

При нативной установке рабочим каталогом должен быть каталог, содержащий
`files/` и `lib/`. В `lib/` должны находиться `libgostcrypto.so` и
`libcpblindsig.so`, собранные/полученные по инструкции официального
инструмента. Нужен Node.js 16 (пакет `ffi-napi` не рассчитан на современные
версии Node). Для нативного запуска нужна CSP 5.0.13000 или новее: в
проверенной конфигурации CSP 5.0.12000 не поддерживает `KP_MULX`, и операции
на кривой завершаются ошибкой:

```text
cd /data/edg2025-official
LD_LIBRARY_PATH=/opt/cprocsp/lib/amd64 \
node /path/to/deg2025/observer-tools/dist/index.js validate \
  D6amFqdazz8DxfxUxmFZKpFioXhhEXQ3jkgRMeab1A4t
```

Для полного набора запускать отдельный Node-процесс на каждое голосование
дорого. Подготовьте сбалансированные каталоги:

```text
python3 feddeg/verification/official/make_batches.py \
  --base /data/edg2025-official --batches 24
```

Затем из каждого `/data/edg2025-official/batches/batch-NN` запустите
`observer-tools/dist/index.js validate` без идентификатора. В batch-режиме
имя ссылки обязано быть `<contract-id>_dump.zip`; это автоматически делает
`make_batches.py`. Если ОС не разрешает симлинки, используйте `--copy`
(потребуется существенно больше места).

Для профилирования официальная утилита поддерживает отключение проверок:

```text
# Только сопоставимый быстрый проход без проверок ZKP бюллетеней:
node .../dist/index.js validate <contract-id> --no-zkp

# Все три проверки бюллетеня/транзакции отключены:
node .../dist/index.js validate <contract-id> \
  --no-zkp --no-blind-sig --no-tx-sig
```

## Измеренные времена

Ниже — измерения официальной утилиты на дампе 2025 года, Ubuntu 24.04,
16-ядерный ноутбук, запуск ограничен четырьмя ядрами. Это ориентир, а не
гарантия времени на другой версии CSP, Docker или Node.js.

| Сценарий | Размер | Время | Нормировка |
|---|---:|---:|---:|
| Полная проверка, губернатор Пермского края | 2 520 бюллетеней, 6 ZKP-ячеек/бюллетень | 24,8 s wall; 4,98 s CPU | **0,23 ms CPU на бюллетень** только на ZKP |
| Та же выборка с `--no-zkp` | 2 520 бюллетеней | 4,40 s CPU | разность с полной проверкой: 0,58 s CPU |
| ZKP-ячейка официального CSP | — | примерно 38 μs | 6 ячеек дают примерно 0,23 ms/бюллетень |
| Итоговый проход с `--no-zkp --no-blind-sig --no-tx-sig` | одна выборка | 3,41 s CPU | результат/агрегация/состояние за **одно голосование** |
| Крупное голосование | 27 645 бюллетеней | 230,7 s wall; 703 s CPU | время заметно зависит от хвоста агрегации и DLP |

В полном дампе среднее число проверяемых range-proof ячеек — около 6,8 на
принятый бюллетень. У официальной программы нет отдельного флага, который
выводил бы только время `DecAgg`; поэтому строка с отключенными тремя
проверками — честная верхняя граница финального прохода, куда также входят
чтение CSV и агрегация шифротекстов. Для собственного запуска сохраняйте
вывод `time` и явно указывайте число ядер.

Особенности адаптера:

- `type:105` с вложенным `type:103/104` превращается в строку транзакции;
- `base64:` у бинарных data entries снимается только в CSV-представлении;
- строка `rollback` оставляется пустой, если в дампе нет rollback-маркера;
- потерянные ведущие нули `blindSigParams` восстанавливает сам официальный
  инструмент при чтении состояния;
- проверка по одному `contract-id` надежнее batch-режима, потому что не
  зависит от правила извлечения идентификатора из имени файла.

## Docker

`Dockerfile` собирает официальный инструмент из фиксированной ревизии
`cikrf/deg2025` (`d1fc451622342990e436afdc5849e6e9969f62c7`) и устанавливает
CryptoPro CSP 5.0.13000. Тестовые наборы в образ не входят. Внешний каталог
`official-run/` не нужен. На ARM нужна эмуляция x86-64. Для сборки нужен
интернет; SHA-256 архива CSP проверяется до установки. SHA-256 включённого
`cpblindsig.zip`:
`aee1e8cbf32946e666c9ef7fd24467122303ee3cfb9f1cf674065160265b56e1`.

```sh
docker build --platform linux/amd64 -t feddeg-official-bugs .
docker run --rm --platform linux/amd64 \
  feddeg-official-bugs validate <contract-id> [флаги]
```

- [`unlinked_sum/`](unlinked_sum/) — пример с несвязанным доказательством
  суммы, скриншот и отдельный Dockerfile поверх основного образа.
- [`test_data/`](test_data/) — копия флешки от 18 сентября 2026: семь почасовых
  официальных выгрузок одного голосования, контрольные суммы и переносимые
  скрипты сбора. Это неполное окно, без расшифровок и итогов.

Проверка данных с флешки:

```sh
docker run --rm --platform linux/amd64 \
  -v "$PWD/test_data:/app/files:ro" \
  feddeg-official-bugs validate \
  2V8q3LAJqY6cYzCSAkhyeSomQGqEaA9KQtGjjWWRs537
```

Ожидается 1164 выданных бюллетеня и 1161 принятый голос без ошибок подписей
и ZKP, затем `Не хватает данных для проверки расшифровок`. Это неполная
проверка, не подтверждение итогов голосования.
